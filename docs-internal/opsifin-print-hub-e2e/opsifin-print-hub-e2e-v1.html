Ruang lingkup dan cara membaca

Dokumen dibuat dari working tree Hub saat ini, PRD, kontrak Agent v1, skema MySQL lokal, data lokal, dan pemeriksaan sekunder repo Agent 0.3.11. Lingkungan lokal yang diperiksa memiliki 28 tabel, 187 print job, 989 event, 87 snapshot dokumen, 202 callback terkirim, dan tidak memiliki trigger database. QA2, production, jaringan tiap tenant, serta seluruh model printer fisik belum diaudit. Kartu berlabel Runbook menjelaskan alur yang sudah ada; kartu berlabel Perbaikan adalah pekerjaan yang belum boleh dianggap selesai. Tautan bukti menunjuk tepat ke file dan baris working tree Hub.

Tujuan dokumen

  1. Memberi satu gambaran end-to-end yang bisa dibaca developer, support, dan operator tanpa harus menelusuri seluruh source code.
  2. Menunjukkan batas tanggung jawab: opsifin-main menentukan dokumen, Hub mengatur trust/routing/state, dan Agent melakukan pekerjaan fisik.
  3. Menjadikan tenant, Integration Identity, Source Connection, binding, dan claim sebagai rantai kepercayaan yang tidak boleh dilompati.
  4. Menutup risiko cetak ganda dan kebocoran lintas tenant sebelum pilot, tanpa mengubah aplikasi menjadi microservices atau menambah komponen yang belum dibutuhkan.
  5. Menyediakan matriks QA yang dapat dipakai sebagai gate onboarding tenant dan gate rilis Agent/Hub.

AS-IS

Kondisi implementasi saat audit

85 test / 514 assertions terakhir · 1 tenant lokal · Agent 0.3.11

Pipeline utama sudah berjalan sampai printer fisik dan callback. Redis/Horizon aktif untuk background PDF refetch dan OTA; source pull serta callback MVP masih berjalan langsung di scheduler.

Control plane & trust

  • Hub bersifat internal-only; tenant adalah master parent seluruh resource.
  • Integration ID Hub harus sama dengan respons /identity opsifin-main.
  • Connection yang berubah atau gagal verifikasi menjadi inactive; binding terkait ikut dinonaktifkan.
  • Agent token membawa tenant secara implisit dan request selalu memasang TenantContext.

Pipeline dokumen

  • Pull /getData → dedupe → validasi PDF → snapshot SHA-256 → queued.
  • Agent claim setiap 5 detik, lease 120 detik, signed URL 5 menit, satu job aktif per printer.
  • Agent mengirim event idempoten dari SQLite outbox; Hub menyimpan timeline append-only.
  • Terminal state membuat callback outbox dengan retry 30s / 120s / 600s / 1800s / 3600s.

Data lokal saat audit

  • Print job: 77 failed, 10 printed, 100 skipped.
  • Callback: 202 sent; 5 refetch request berstatus succeeded.
  • Tersimpan 87 dokumen dan 989 event; belum ada job retensi terjadwal.
  • Seluruh tabel bisnis inti memiliki tenant_id dan index komposit yang relevan.

Batas bukti

  • Working tree memuat banyak perubahan belum di-commit; audit merekam kondisi aktual, bukan hanya commit terakhir.
  • Repo Agent diperiksa untuk recovery spool journal dan outbox, tetapi tautan artifact difokuskan ke repo Hub.
  • QA2/production, TLS, backup-restore, load test, dan variasi driver printer belum diverifikasi.
  • Tidak ada trigger MySQL lokal; aturan domain berada di aplikasi dan constraint database.

Aturan keselamatan yang sudah berlaku dan wajib dipertahankan

  1. Tenant selalu eksplisit. Model bisnis memakai BelongsToTenant; tanpa context query kosong dan create ditolak.
  2. Identity fail-closed. Source hanya operasional bila integration_id remote sama persis dengan tenant Hub.
  3. Binding adalah route. Source identity dan destination printer dipindahkan bersama saat manual retry; route lintas source ditolak.
  4. Dedupe tidak dihapus. Kunci unik tenant + InvNo + ItemType + VersionInv mencegah getData berulang mencetak dua kali.
  5. Snapshot menjadi bukti. Agent mengunduh dari signed URL Hub dan mencocokkan SHA-256 sebelum mencetak.
  6. Event idempoten dan append-only. event_id yang sama diterima sebagai duplicate, bukan diproses ulang.
  7. Error setelah spool tidak auto-retry. Jalur print_error sudah menghentikan job sebagai failed karena hasil fisik ambigu.
  8. Retry tidak menghapus histori. Run, attempt, dokumen, event, callback lama, destination lama/baru, reason, dan actor tetap dapat diaudit.
  9. Availability mengikuti Agent. Printer tidak boleh terlihat Online bila heartbeat Agent stale/offline/revoked.
  10. Mulai sederhana. Docker Compose + Laravel + MySQL + Redis/Horizon tetap cukup; tidak perlu Kafka, Kubernetes, atau database per tenant.
TANYA

Keputusan bisnis yang masih terbuka

6 pertanyaan · masing-masing dengan rekomendasi

D1 · State saat lease habis setelah spooled

Kode sekarang mengembalikan claimed dan printing ke queued. Jalur print_error sesudah spool justru berhenti sebagai failed karena risiko duplicate.

Rekomendasi: claimed sebelum spool tetap queued; printing/spooled menjadi failed dengan PRINT_RESULT_UNKNOWN dan menunggu rekonsiliasi operator. Hindari state baru dulu agar perubahan tetap sederhana.

D2 · Siapa boleh mengonfirmasi kertas sudah tercetak?

Tanpa aksi confirm, satu-satunya pemulihan adalah retry yang mungkin mencetak invoice kedua.

Rekomendasi: Platform Admin, Tenant Admin, dan Operator tenant boleh Confirm physically printed hanya untuk failure ambigu, dengan dialog dua tahap, reason wajib, audit, dan bukti spooler JobId.

D3 · Kebijakan host Link PDF

Sebagian instance dapat menghasilkan Link dengan host berbeda atau internal, jadi aturan same-host mutlak berisiko memutus tenant yang valid.

Rekomendasi: Default host Base URL + allowlist host tambahan per connection. Tolak loopback/link-local/metadata/private yang tidak disetujui dan validasi setiap redirect.

D4 · Retensi snapshot dokumen

PRD menyebut 90 hari, tetapi data lokal belum memiliki expiry aktif dan belum ada purge.

Rekomendasi: Default 90 hari per tenant, metadata + SHA tetap permanen sesuai retensi histori, dukung legal hold sebelum pilot production.

D5 · Kapan source pull dipindah ke Horizon?

Scheduler serial cukup untuk satu binding lokal, tetapi tidak memenuhi isolation/jitter dan mudah mengalami head-of-line blocking saat tenant bertambah.

Rekomendasi: Kerjakan sebelum pilot multi-tenant, tetap dalam monolith: scheduler dispatch, Horizon worker, unique lock binding, throttle dua request per tenant.

D6 · Callback setelah melewati 24 jam

Saat ini pending callback bisa melewati expiry bila source inactive dan terkirim kemudian saat source aktif kembali.

Rekomendasi: Tandai expired, alert operator, dan jangan kirim otomatis. Recovery wajib action manual dengan reason agar perubahan terlambat di opsifin-main dapat diaudit.
