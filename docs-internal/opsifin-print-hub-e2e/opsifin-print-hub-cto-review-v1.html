Batas klaim dan cara membaca

Audit membaca implementasi Hub, kontrak API, migrasi, test, PRD/progress, source Python lama, serta checkout source Agent. Docker Desktop tidak aktif pada 11/11/2026, sedangkan PHP lokal 8.4 tidak memenuhi kebutuhan 8.5; karena itu suite tidak dapat dijalankan ulang hari ini. Bukti terakhir di docs/PROGRESS.md adalah 85 test/514 assertion pada 10/11/2026. Benchmark printer fisik, load, chaos, backup-restore, dan pilot produksi belum memiliki artefak hasil. Semua angka latency di dokumen ini adalah model estimasi sampai telemetry benchmark tersedia. Checkout resmi Agent juga masih berupa spike B2/placeholder, walau progress Hub mencatat paket Agent 0.3.11 pernah berjalan; ketidaksesuaian source-of-truth ini harus ditutup sebelum approval CTO.

Keputusan eksekutif

  1. Arsitektur baru lebih tepat secara strategis dibanding Python lama untuk keamanan credential, observability, pengelolaan banyak tenant, idempotency, retry, audit, dan distribusi update.
  2. Belum boleh disebut production-proven. Status yang bertanggung jawab adalah pilot candidate with critical gates, bukan siap rollout seluruh tenant.
  3. Untuk sekitar 10 tenant, kapasitas komputasi bukan kekhawatiran utama. Risiko terbesar adalah correctness cetak fisik, duplicate setelah lease timeout, single point of failure, source Agent yang tidak sinkron, dan kesiapan operasional.
  4. Jangan sederhanakan safety controls. Simplifikasi dilakukan pada onboarding, istilah UI, status operator, dan deployment; identity check, tenant scope, lease/idempotency, snapshot/hash, outbox, event history, serta audit harus tetap ada.
  5. Go/no-go ditentukan oleh bukti. Pilot hanya boleh dimulai setelah source Agent direkonsiliasi dan gate printer, duplicate, recovery, capacity, serta tenant isolation lulus dengan hasil tersimpan.

VERDICT

Kondisi arsitektur per 11 November 2026

Design: kuat · Hub: advanced MVP · E2E proof: belum lengkap

Hub sudah memiliki control plane multi-tenant, identity verification, binding, job state machine, lease, event idempotency, PDF snapshot/hash, callback outbox, manual retry, heartbeat, audit, dan OTA. Namun beberapa janji PRD masih belum terbukti atau belum tersedia sebagai source yang dapat diaudit.

Yang sudah memiliki bukti implementasi

  • Identity fail-closed dan isolasi tenant di model/query.
  • Claim memakai transaksi + FOR UPDATE SKIP LOCKED pada MySQL.
  • Event Agent idempoten, callback outbox dengan retry/backoff.
  • PDF divalidasi, di-hash, dan disimpan sebagai snapshot per tenant.
  • Presence Agent dan availability printer dihitung dari heartbeat, bukan status mentah saja.
  • Manual retry/refetch menjaga history, reason, dan destination binding.

Yang belum boleh diklaim selesai

  • Source Agent produksi yang cocok dengan paket 0.3.11 belum ada pada checkout resmi.
  • B1–B7 belum memiliki laporan hasil terukur; load test/chaos test tidak ditemukan.
  • Backup-restore, TLS production, alerting, runbook, retensi dokumen, dan pilot belum ditutup.
  • Jalur lease kedaluwarsa setelah spooled masih berpotensi requeue hasil ambigu.
  • Scheduler source/callback masih serial langsung, belum memakai worker per binding.
  • Test utama memakai SQLite sehingga jalur lock MySQL belum dibuktikan oleh suite yang sama.

BL

Komparasi: Python lama, implementasi sekarang, dan target

2 task GoodDay

Arsitektur baru menang pada operability dan correctness design, tetapi menambah komponen serta dependency pusat. Perbandingan harus memakai tiga kolom, bukan membandingkan kode lama dengan target ideal yang belum terbukti.

Python lama: keunggulan nyata

  • Sangat sederhana: satu proses langsung ke opsifin-main dan printer.
  • Blast radius kecil; PC lain tetap mencetak bila satu PC gagal.
  • Sedikit hop sehingga kertas dapat mulai keluar cepat setelah data ditemukan.
  • Sudah lama kompatibel dengan printer yang berjalan di user session.

Hub + Agent: keunggulan nyata

  • Credential hanya di Hub; device token dapat dicabut.
  • Satu Agent dapat melayani banyak printer di PC/site.
  • Tenant/source/printer/job memiliki identity eksplisit dan audit terpusat.
  • Snapshot + SHA-256 + state machine + event + outbox membuat failure dapat ditelusuri.
  • Konfigurasi dan update dapat dilakukan terpusat, tanpa kunjungan setiap PC.

PF

Berapa lama print dan apakah 10 tenant aman?

2 task GoodDay

Latency harus dibagi menjadi time-to-detect, time-to-spool, paper-out, final verification, dan callback. Satu angka saja menyesatkan.

Model default baru (pull 30s)

  • Deteksi invoice: rata-rata ~15s, p95 ~29s.
  • Fetch + validate + save PDF: target 1–10s, tergantung opsifin-main/PDF.
  • Claim Agent: rata-rata ~2.5s, maksimum normal ~5s.
  • Download Agent + spool: target 1–5s.
  • Kertas mulai keluar: tipikal ~20–45s setelah invoice ready, belum dibenchmark.
  • Final printed: tambah verifikasi 60s; tipikal ~80–105s.
  • Callback source: tambah scheduler 0–10s; tipikal ~90–115s.

Jika pull interval 120s

  • Deteksi rata-rata ~60s, p95 ~114s.
  • Kertas mulai keluar kira-kira ~65–130s.
  • Final printed/callback kira-kira ~130–200s.
  • Jadi pull interval sangat berpengaruh pada latency awal, tetapi tidak mengubah jendela verifikasi 60s.
  • Angka harus dikonfirmasi telemetry p50/p95 per tahap.

TANYA

Keputusan bisnis yang masih terbuka

3 pertanyaan · masing-masing dengan rekomendasi

D1 · Apakah approval yang diminta sekarang untuk pilot atau langsung production?

Bukti yang tersedia belum memenuhi production approval seluruh tenant.

Rekomendasi: Minta approval controlled pilot setelah blocker AUD-01/AUD-02 ditutup dan GT-01 s.d. GT-03 lulus.

D2 · Berapa retensi snapshot PDF yang disetujui legal/finance?

PRD menyebut 90 hari, tetapi proses pruning belum ada dan data invoice lintas tenant disimpan terpusat.

Rekomendasi: Mulai 90 hari terenkripsi dengan override tenant; metadata/hash/timeline lebih panjang sesuai audit policy.

D3 · Apa definisi bisnis 'berhasil tercetak'?

Windows spooler tidak dapat membuktikan secara absolut bahwa lembar fisik diterima pengguna.

Rekomendasi: Gunakan tiga milestone: Spool accepted, Printed verified, dan Printed unverified; jangan menjanjikan kepastian fisik 100%.
